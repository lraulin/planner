## The Postponed question, answered

Short version: **the plan to link the two fields is fine — it was just implemented in most
places rather than all of them.** No reconsideration needed in the morning.

The frozen `2026-08-01-2145-deferred-date-model` spec already decided exactly what you
described: `postponed` is the state, `deferred_date` is its expiry, and **expiry is derived
at read time, never swept** — no midnight job, no clock in the database. A routine you tick
off today gets `postponed` + tomorrow's date, and tomorrow it simply reads Not started
again with nothing having written to the row.

That was true in `sliceTree` (the Show Postponed toggle), in the Chooser, and in the Status
column. It was **not** true in the State column — which is the one place you actually look,
and the one your filters run on. `stateColumn` / `abbrStateColumn` read `row.node.state`
raw, so the morning after, the cell still said Postponed, and a view with Postponed unticked
hid the cat litter for good. Grouping by State had the same stale reading.

Fixed rather than redesigned. `ownEffectiveState` collapses an expired own shelf, and the
State column, its abbreviated twin, and the State grouping dimension all use it.

## Needs a decision

- **Should the State column show a shelf inherited from an ancestor?** I made the column
  read the row's _own_ effective state, so a task under a postponed project still shows its
  own state — because the cell is an editable `<select>` and has to say what writing to it
  would change. The alternative (full inherited `effectiveState`) would make the column
  agree with the Status column and with what the row hides with, at the cost of a dropdown
  that displays Postponed while writing to it changes something else. **Recommendation:**
  leave it as shipped; if the inherited case matters, make the shelved-by-an-ancestor rows
  read-only or visually marked rather than mislabelled.
  — blocking: nothing; both readings are coherent today.
  — **Resolved 2026-08-07:** left as shipped (`ownEffectiveState`). Detail form still shows
  stored state beside Deferred until — same deliberate call.

- **Sorting the State column is alphabetical, not workflow order.** `sortValue` returns the
  enum value, which happens to sort identically to the labels (Cancelled, Completed,
  Delegated, In progress, …). Achieve's own order — the one the dropdown uses — is Not
  started, In progress, Waiting, Completed, Postponed, … `slice.ts` already gives Priority
  and Deadline explicit orders for exactly this reason ("an order that is meaningful rather
  than incidental") and deliberately did _not_ give State one, which reads like an open
  question rather than an oversight. **Recommendation:** switch to Achieve order — a state
  column is read as a workflow, not as a glossary. One-line change in `commonColumns.tsx`
  plus a rank array beside `STATE_LABELS`.
  — blocking: nothing.
  — **Resolved 2026-08-07:** `stateRank` / `STATE_ORDER` drive State column sort and
  group-by-State.
