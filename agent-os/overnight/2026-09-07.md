## Needs a decision

- **What should ACHXML import do with a cyclic parent link?** `lib/achieve/import.ts:154`
  maps `parentAchId` → `parentId` and writes it unvalidated, so a corrupt export can put a
  `parent_id` ring in the database. As of `ee198b1` nothing hangs on one any more, but the
  nodes on the ring still vanish from the Outline silently — `derive.ts` requires
  depth-first parents-before-children order and drops what it cannot place, with no notice.
  Options: (a) detect at import and drop the offending parent link so the branch lands at
  the root where it can be seen and fixed; (b) refuse the whole import with a message
  naming the rows; (c) leave it and add a notice on the Outline when derive drops rows.
  **Recommendation: (a), and more strongly than when I first wrote this** — the _note_ half
  of that same importer already does exactly (a). `lib/achieve/import.ts:487` resolves note
  parents in rounds and, when a round makes no progress, lands the remainder at the root
  with `Note "…" could not resolve parent; imported at root`. So the file already contains
  the pattern, the warning vocabulary, and the decision; the node half just never got it.
  That makes this closer to an inconsistency than a design question — but it still changes
  what an import does, so it stays yours. Not taken tonight.
  — blocking: nothing; every hang it could cause is fixed as of `acc2253`.

- **Should filing work into a settled parent reopen it?** The organizer writes
  `state: "not_started"` on five paths while moving an inbox item under a chosen parent,
  and `requireDestinationParent` never checks whether that parent is settled — so you can
  file fresh work under a Completed project and get the same contradiction `316f10f` just
  fixed. I did **not** treat this as the same bug: `moveNode` behaves identically, so the
  organizer is consistent with every other move in the app. The real question is whether a
  _move_ into a settled destination should reopen it the way a _state transition_ does.
  **Recommendation: yes, upward only** — the rule "a parent's state is a claim about the
  work beneath it" does not care which gesture put the work there — but it changes drag-
  and-drop behavior across the whole outline, which is your call, not a 10pm one.
  — blocking: nothing.

- **Budget templates has no way in.** `applyBudgetTemplates` (plus
  `budget/templates/{apply,suggest,monthSpan}.ts`, all three tested) is reachable only from
  `applyBudgetTemplatesAction`, which no component imports —
  `specs/2026-08-24-1311-budget-assign-options` said "Replace `applyBudgetTemplatesAction`
  usage" and the replacement left the action behind. So the feature exists, is tested, and
  cannot be run. Either wire it to a command or delete the action and the three modules.
  I left all of it alone: unlike the four actions in `5cb5b4c`, deleting this one discards
  a real capability rather than a duplicate path.
  — blocking: nothing.

## How the bugs were found

Five real defects — one of them in thirteen places — and all five came from the same detector rather than from reading code
for smells: **find a claim the codebase makes about itself, then check the code against
it.** The claims were a docstring ("the app's one cycle check"), a frozen spec ("ranks are
dense 1..n and unique"), a helper's stated reason for existing ("rather than writing the
letter and rank verbatim"), and a planner's own output (`retainedFields`). In each case
some caller had been written without knowing the claim existed.

That also explains the shape of what is left: this codebase's characteristic defect is not
bad logic, it is **a second implementation written by someone who did not know about the
first**. `isSelfOrDescendant` five times, `isRealDate` six, `shiftDateKey` three, four
paths writing a priority where one engine was supposed to. The sweeps that found nothing
are worth recording too — every `update`/`delete` checked for a missing `userId` (none),
57 query functions hand-checked for cross-user scoping (all correct), recurrence patterns
against month-end and DST (correct), `bulkResetScopes` against the missed-key class
(enumerates what is stored, so it cannot miss one), and the Overdue promise
(`overdue` structurally requires a deadline, and recurrence never creates one).
