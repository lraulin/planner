## Needs a decision

- **What should ACHXML import do with a cyclic parent link?** `lib/achieve/import.ts:154`
  maps `parentAchId` → `parentId` and writes it unvalidated, so a corrupt export can put a
  `parent_id` ring in the database. As of `ee198b1` nothing hangs on one any more, but the
  nodes on the ring still vanish from the Outline silently — `derive.ts` requires
  depth-first parents-before-children order and drops what it cannot place, with no notice.
  Options: (a) detect at import and drop the offending parent link so the branch lands at
  the root where it can be seen and fixed; (b) refuse the whole import with a message
  naming the rows; (c) leave it and add a notice on the Outline when derive drops rows.
  **Recommendation: (a)** — an import that half-succeeds is worse than one that lands
  everything somewhere visible, and the root is the honest place for a branch whose parent
  is unrepresentable. Not taken tonight because it is a behavior choice, not a defect.
  — blocking: nothing; the hang is already fixed.

- **Should filing work into a settled parent reopen it?** The organizer writes
  `state: "not_started"` on five paths while moving an inbox item under a chosen parent,
  and `requireDestinationParent` never checks whether that parent is settled — so you can
  file fresh work under a Completed project and get the same contradiction `316f10f` just
  fixed. I did **not** treat this as the same bug: `moveNode` behaves identically, so the
  organizer is consistent with every other move in the app. The real question is whether a
  _move_ into a settled destination should reopen it the way a _state transition_ does.
  **Recommendation: yes, upward only** — the rule "a parent's state is a claim about the
  work beneath it" does not care which gesture put the work there — but it changes drag-
  and-drop behavior across the whole outline, which is your call, not a 10pm one.
  — blocking: nothing.
