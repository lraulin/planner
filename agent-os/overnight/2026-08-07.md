## Needs a decision

- **Four places assume the server runs in your timezone. On Vercel it runs in UTC.** This
  came out of the test-timezone work and is the most valuable thing in this report. Every one
  of these is correct on the laptop, where the Next.js process really is in `America/New_York`,
  and wrong on the deployed app. Demonstrated rather than assumed — at 22:15 tonight,
  `localDateKey(new Date())` returns `2026-08-07` under `TZ=America/New_York` and
  **`2026-08-08`** under `TZ=UTC`. So the window is roughly 20:00 → midnight Eastern, every
  evening, which is exactly when a day page gets used.

  1. **`src/app/day/page.tsx:20`** — a server component computes
     `today = localDateKey(new Date())` and uses it for both the default day and the
     carry-forward gate. In that evening window, opening `/day` on the phone lands on
     **tomorrow's** page, and because `day === today` is then true, `loadDay` runs
     `forwardOpenItems(userId, tomorrow)` — carrying today's unfinished lines forward before
     today is over. `day/queries.ts:81`, `day/mutations.ts:369` and `day/sync.ts:109` carry
     the same `localDateKey(new Date())` default, and the `sync.ts` one is what decides which
     day a behind-schedule task's open line sits on.
  2. **`src/lib/detail/mutations.ts:72,415,516`** — the same server-day value decides whether
     a shelf has expired and drives `stateFromDates`.
  3. **`src/lib/google/mapping.ts:232`** — `localTimeZone()` is documented as "the machine's
     IANA zone — this is a single-user app running in its owner's timezone". Both halves have
     since stopped being true: `specs/2026-08-01-1042-multi-user-accounts` shipped, and on
     Vercel the machine is UTC. Nothing ever passes a zone in, so **every** appointment written
     to Google carries `timeZone: "UTC"`. For a recurring event that is the case the comment
     right below it says the field exists for — Google expands the RRULE in the named zone, so
     a weekly 09:00 drifts an hour across DST.

  4. **`src/lib/schedule/geometry.ts:96`** — `startOfWeek` returns **process-local midnight**,
     and `weekly_plans.week_start` stores exactly that. This is the worst of the four, because
     it does not merely display the wrong day: `getWeeklyPlan` (`planning/queries.ts:28`) and
     `ensureWeeklyPlan` (`planning/mutations.ts:41`) both look the row up with **exact
     timestamp equality**, and `ensureWeeklyPlan` inserts when the lookup misses. So the same
     week normalizes to three different instants depending only on where the process runs —
     measured, for the week of Aug 2 2026:

     | Server zone        | Stored `week_start`        |
     | ------------------ | -------------------------- |
     | `America/New_York` | `2026-08-02T04:00:00.000Z` |
     | `UTC` (Vercel)     | `2026-08-02T00:00:00.000Z` |
     | `Europe/Berlin`    | `2026-08-01T22:00:00.000Z` |

     Plan a week on the laptop and open the wizard for the same week on the deployed app and
     you get a **second row**, which `weekly_plans_user_week_uq` cannot catch because the two
     values genuinely differ. Note Berlin lands on a different calendar date altogether.
     Unlike (1)–(3), fixing this one also means rewriting stored rows, so it wants a migration
     as well as a decision — which is the other reason I left it.

  This is `dates.md` rule 8 ("no business rule may depend on the server's `TZ`") being broken
  in the one direction the rule was written about. I did not fix it because every fix is a
  design choice I should not make unattended: thread the browser's day/zone through from the
  client, store a per-user timezone on the account (which is the honest answer now that the
  app is multi-user), or set `TZ` on the deployment — and that last one I am told not to touch.

  **Recommendation: a per-user timezone on the account**, defaulted from
  `Intl.DateTimeFormat().resolvedOptions().timeZone` at first sign-in. It is the only one of
  the options that is still right when the second account is in another zone, and it feeds all
  four sites from one value. Worth a small spec, with (4) carrying a migration that re-encodes
  existing `week_start` rows.
  — blocking: correct evening behaviour of `/day` on the phone, and correct DST expansion of
  every recurring appointment Planner writes to Google.

- **Settling from the detail drawer and the day page does not settle the work underneath —
  and the grids do.** This is last night's follow-up 1, and it is worse than a missing
  confirmation: `detail/mutations.ts:562` and `day/mutations.ts:187` call
  `reopenSettledAncestors`, which is deliberately **upward only** (`tree/mutations.ts:1029`
  says why — the downward half is gated behind a confirmation these surfaces do not have).
  So completing a project from its drawer leaves its open tasks open, while completing the
  same project from `/projects` settles them after asking. Same gesture, two different
  database states depending on which surface you were looking at.

  Why I did not just fix it: the confirmation needs the open-descendant count, and neither
  surface has the subtree client-side. There are three defensible ways to get it and they
  are not equivalent — (a) add `openDescendantCount` to the detail payload and the day rows,
  (b) a dedicated server action called when a settling state is picked, (c) have the mutation
  refuse and return "needs confirmation", re-submitted with a flag. (c) changes the
  `ActionResult` contract for every caller; (b) adds a round trip on every state pick; (a)
  costs one extra query per drawer open and is closest to how the grids already work.

  **Recommendation: (a)**, as a small delta-spec rather than an unattended 3am diff — it
  changes what Save does on two surfaces and deserves acceptance criteria.
  — blocking: nothing else; it has been true since the cascade shipped.
