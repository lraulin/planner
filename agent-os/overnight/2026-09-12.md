## Needs a decision

- **Check one thing on production: does Neon order `sort_key` bytewise?** Everything that keeps
  siblings in order assumes it. `sortKey.ts` says its `compare` "matches Postgres' bytewise
  ordering", and 26 queries `ORDER BY sort_key`, several of them (`siblingKeys`,
  `tree/mutations.ts:113`) feeding neighbours to `between()`, which **throws** on
  out-of-order input. But the columns are plain `text` with no `COLLATE`, so the order is
  whatever the database's collation says. Locally that is `en_US.utf8` on
  **`postgres:17-alpine`**, and musl collates every locale like `C`: the container returns
  `G V l t`, which is bytewise. glibc or ICU `en_US` returns `G l t V`. Real keys mix cases
  from the eleventh sibling on (I generated forty with `between()` to check). **No test in the
  gate can see the difference**, because every integration test runs on Alpine. The claim
  arrived as a side remark in `d493febe`, a budget commit, and nothing verifies it.

  The check, in the Neon SQL editor:
  `select datcollate, 'V' < 'l' as bytewise from pg_database where datname = current_database();`
  If `bytewise` is **true**, nothing to do. If it's **false**, long sibling lists sort
  differently in SQL than in JS, and inserting or moving past the tenth sibling can throw
  "Cannot find a key between". Fix the model, not the callers: an additive migration giving
  every `sort_key` column `COLLATE "C"`, so the order is the schema's rather than the
  server's. The fact that it hasn't been reported suggests production is fine, but it's
  one query to know. — blocking: nothing tonight; it decides whether that migration is needed.

- **Un-shelving a task leaves its future deferred date behind, and that date then blocks
  planning it.** Pick Not started on a task postponed until Nov 1, from a grid or the drawer:
  the state changes and `deferred_date` stays Nov 1. `ownShelf` ignores it, since only a
  `postponed` row is shelved, but three other places don't:
  - **Week plan / day drop** refuses with _"… is deferred until 2026-11-01, so it cannot be
    planned for 2026-09-14"_ (`day/sync.ts:345`). That checks the date and not the state, so it
    names a shelf you already removed.
  - **Dragging its day line** to another day (`day/mutations.ts:269`) writes a target start
    before Nov 1 with no check, and `nodes_start_not_before_deferred` rejects it as a raw
    constraint error.
  - **Typing a start date in the drawer** trips `planPrecedesShelf` (`detail/mutations.ts:484`),
    which _silently clears the plan you just typed_ in favour of the residue.

  The 08-01 spec (frozen) says "changing the state un-shelves it" and nothing about the date.
  Options: (a) clearing a **future** deferred date whenever the state leaves `postponed` for
  anything unsettled. That's what `reopenDayLine` already does (`tree/mutations.ts:1200`,
  "only a future shelf is cleared"), and it's the only reading the constraint allows. Its cost
  is that re-shelving means retyping the date. (b) Make the constraint and all three readers
  state-aware, which needs a migration. **Recommendation: (a)**, a few lines in
  `applyStateTransition` beside tonight's `955a15f3`, with a delta note on the 08-01 spec. I
  didn't ship it because it discards a date you entered, in a frozen spec's area. — blocking:
  planning any task you've un-shelved by hand.

- **Normalise the old date encoding once, instead of making every reader tolerate it.** Plan
  dates written before `dates.md` settled on UTC noon are stored at local midnight (`04:00Z` /
  `05:00Z`); locally that's most of them. Readers that go through `toDateKey` are fine, but
  anything comparing instants isn't. Tonight's `5f5fa872` was one such place. Another is
  **the database constraint itself**: `nodes_start_not_before_deferred` compares timestamps,
  so a target start stored at `04:00Z` counts as _before_ a same-day deferred date written at
  `12:00Z`. The drawer escapes that because it re-posts every date, but a deferred-date-only
  write (`update_node` from the agent API) on such a row is be rejected with a raw
  constraint error. I checked with a throwaway probe: start `2027-03-01T05:00Z` plus deferred `fromDateKey("2027-03-01")` → `Failed query: update "nodes" set "deferred_date"…`. Options: (a) a one-off data migration rewriting each calendar column to
  noon UTC of its own `toDateKey` day, same day and new encoding, the model fix; (b) keep
  finding the instant comparisons one at a time. The writer that produced the old encoding, the
  Achieve importer, is fixed tonight (`c18cf1fb`), so a migration would stay done.
  **Recommendation: (a)**, run against a Neon
  branch first. It rewrites every row's value, which is why it wasn't an overnight job. Worth
  checking production's share first:
  `select count(*) filter (where extract(hour from deferred_date at time zone 'UTC') <> 12) from nodes;`

## Noticed but didn't touch

- **`get_context` tells an agent that shelved work is open.** Its `topOpenWork`
  (`agent/outlineTools.ts:67`) keeps A/B/focus tasks and projects whose _stored_ state isn't
  settled. So a routine between cycles, or an A-priority project postponed to February, is
  reported as current work, and an agent asked "what should I do today" can recommend it. The
  grids and the Chooser read `effectiveState` for exactly this reason. It's a one-line filter
  change (`effectiveState(n.state, n.shelf, today) !== "postponed"`), but it changes what an
  agent is told, and `date-model.md` only names grids and the Chooser, so I left it.

- **On the laptop dev server, the Google mirror probably deletes the all-day events on the day
  before the week you're viewing.** This is reasoning, not a reproduction; I have no Google
  access. `listEvents` asks for events whose end is strictly after `timeMin`, and an all-day
  event's exclusive end is midnight _in the calendar's zone_. `syncWindowFor` starts the window
  at the server's local Sunday midnight. On a New York server that is 04:00Z, exactly where
  Saturday's all-day event ends, so Google leaves it out. But the mirror stored that event's end
  as UTC noon (`readEventTime` → `fromDateKey`), so `overlapsWindow` says it's in the window,
  it's "unseen", and `planMirror` deletes it. It comes back as a fresh row when you look at
  that week, **without its local-only columns**: check state, project link, contexts. On
  Vercel (UTC) the window starts four hours earlier and the event is returned, so production
  should be unaffected for you. The TZ-proof fix is to fetch one day wider on each side than
  the window the sweep is allowed to delete from. I left it because this is the one module
  that deletes calendar rows, and I couldn't confirm Google's boundary against the real API.

- **A metric value of `12,345` saves as 12.345.** `parseMetricInput` reads a comma as a decimal
  point on purpose (`parse.test.ts` pins `"1,618"` → 1.618), so a US thousands separator typed
  or pasted into a value, or sitting in an imported tracking CSV, silently shrinks by 1000×,
  while `1,234,567` is rejected outright. Fine if every metric you track is small; worth
  rejecting a comma followed by exactly three digits if step counts or dollar totals ever go
  in.

- **Job and residence durations stop one day short of the dates' own definition.** The agent
  contract calls `endDate` "Last day at the job" and `movedOut` "Last day at the residence",
  so inclusive. `spanDuration` (`history/span.ts`) measures start → end exclusively, so a job
  held Jan 1 – Dec 31 reads **11m 30d**, not 1y. `span.test.ts` pins the exclusive answer on
  purpose ("2019-03-01 → 2022-06-30" = "3y 3m 29d"), and an ongoing span measured to today
  follows the same rule, so it's a convention, not an accident. If you'd rather a full
  calendar year read as "1y", it's `elapsedParts(start, shiftDateKey(end, 1))` for closed spans
  plus a test change.

- **The agent API can orphan a weekly plan.** `schema.ts:1214` promises "`weekStart` is stored
  already normalized to `weekStartsOn`", and `ensureWeeklyPlan` keeps that promise.
  `updateWeeklyPlan` (`planning/mutations.ts:83`) doesn't: it accepts `weekStartsOn` and
  writes it without moving `weekStart`. Change a Sunday plan to Monday-start and
  `getWeeklyPlan(week, 1)` normalises to the Monday, misses the row, and the wizard starts a
  second plan rather than resuming. The wizard never sends that patch; only
  `update_weekly_plan` does (`agent/planTools.ts:73`). Options: drop `weekStartsOn` from
  `WeeklyPlanPatch` and the tool, since the start day is chosen with the week (my pick); or
  re-normalise `weekStart` on patch, which can collide with a plan already sitting on that
  day. Either way it's an agent-API contract change, so I left it.

- **A day-31 monthly appointment means two different things depending on whether Google is
  linked.** Local series now clamp (Feb 28, Mar 31, Apr 30). A series created with a push
  target goes to Google as `FREQ=MONTHLY` (`google/mapping.ts:215`) and comes back as Google's
  own expansion, which follows RFC 5545 and **skips** months with no 31st — so no February,
  April, June, September or November occurrence at all. The monthly preview can't tell you
  which you'll get. Options: send `BYMONTHDAY=-1` when the start is the last day of its month
  (matches the clamp for the 31st only, not the 29th/30th), or accept the split. It only bites
  on days 29–31, so I'd leave it unless you create such a series.

- **Two more places that only work because you live west of Greenwich.** Neither is worth a
  patch on its own; both belong to the per-user-timezone decision above.
  - `recurrence/pattern.ts` builds its next occurrence as a **local midnight**
    (`new Date(y, m − 1, d)`, lines 94/194/224 — the form `dates.md` rule 4 forbids in shared
    code) and callers re-encode with `toDateKey`. In UTC and every zone west of it, local midnight
    is still that day in UTC, so it reads right; anywhere east of UTC it reads as the day before.
  - `expandRecurrence`'s until check is `toDateKey(start) > toDateKey(recurrenceUntil)`
    (`schedule/recurrence.ts:113`). `start` is a timed **instant**, so on the laptop a 7pm
    Eastern occurrence on the until day (00:00Z the next day) is dropped as past the end. On
    Vercel the expansion runs in UTC anyway, so switching to `localDateKey` would not help
    production. Only local rules hit it; Google series arrive as instances without one.
