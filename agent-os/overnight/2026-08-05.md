- `95f0521` — **Stop the expand command offering the move the row already made.**
  `canExpand` / `canCollapse` say what is _possible_; `commandDeck.ts` read them as the
  row's _state_. So an expanded row's More menu said "Expand selected" and called
  `onExpand` on it, and a collapsed row said "Collapse selected" and called `onCollapse` —
  the toggle already in effect both times, which reads as a dead menu item rather than a
  backwards one. `OutlineGrid.tsx:450` and the row-menu copy at `:559` both feed the same
  builder, so it was wrong in both places. Verified by two new cases in
  `src/lib/grid/commandDeck.test.ts` (both failed first, on label _and_ on which handler
  ran) and in the app: `.artifacts/planner-shots/more-menu.png` shows "Collapse selected ←"
  on an expanded row.

- `9278c80` — **Rebase a zoomed branch against the root it now hangs from.**
  `zoomBranch` corrected only the root and left every descendant carrying its whole-tree
  `depth` and `hidden`. Two consequences. Indentation is drawn straight from `depth`
  (`DataGrid.tsx:1185`), so zooming into a goal three levels down left its children
  indented as though the levels above them were still on screen. And `hidden` means "an
  ancestor is collapsed" — an ancestor _above the root_ still counted, so zooming to an
  item inside a collapsed area rendered the root alone with an empty branch under it.
  That one is reachable by exactly the path the feature exists for, since "Zoom to item…"
  searches the whole outline including collapsed branches. Both rebase in one
  parents-first pass now; a collapse _inside_ the branch is still the user's and survives.
  Verified by 4 cases in `src/lib/tree/zoom.test.ts` (2 new ones failed first) and in the
  app — `.artifacts/planner-shots/zoom-newtasks.png`, where the child now reports
  `aria-level` 2 under a root at 1 instead of 4.

- `b150ec1` — **Stop a conversion to the type a row already is from erroring.** The More
  menu lists every kind, so "Convert to Project" sat there on a Project. Nothing changed
  type, so the transaction skipped its delete branch and went straight to inserting a
  fresh detail row — and every detail table is keyed by `node_id`, so Postgres rejected it
  outright: `duplicate key value violates unique constraint "project_details_pkey"`. Goal
  was the only kind that survived, because the Dream flag gave it an update branch instead
  of an insert. Two clicks from the menu, on Result Area, Project and Task alike.
  `convertNode` now returns early when the kind is unchanged, and the deck keeps the row's
  current kind listed but disabled with "Already a Project" so the menu holds its shape as
  the selection moves. Verified by a new integration case that reproduced the Postgres
  error first, plus a pure case in `commandDeck.test.ts`.

- `4134378` — **Say why priority repair is unavailable instead of ignoring the click.**
  "Remove priority gaps" shipped enabled with nothing selected, while "Reprioritize unique"
  right beside it guarded correctly. Repair is scoped to one sibling group and the selected
  row is what names it, so both hosts (`OutlineGrid.tsx:493`,
  `useNodeCommandDeck.tsx:56`) drop the call when there is no selection — the control just
  never said so. Verified by a new case in `commandDeck.test.ts`, confirmed failing with
  only the source reverted.

- `07a49b4`, `179d483` — **Roadmap caught up with what shipped.** Added the command deck as
  delivered, took expand/collapse-all off the Phase 1 friction list, and noted that the
  Outline's row menu closes part of the older row-context-menu deferral. The second commit
  fixes a claim I got wrong in the first: `rowActions` also synthesises a deck, so the Task
  Chooser has the Open/Rename pair rather than nothing — **Metrics is the only grid with no
  deck**, because it does not go through `GridToolbar` at all.

- `04f4bdd` — **Zoom to the item the search left on screen, not the one it hid.**
  "Zoom to item…" held its own `selectedId` while the query filtered the list under it.
  Search for one item, see it alone with nothing highlighted, press Zoom in — and it zoomed
  to whatever was selected before, which with no current zoom is the first row of the whole
  outline. The rule now lives in `src/lib/grid/pickerSelection.ts` with 4 cases, so the next
  searchable picker gets it for free.

- `1b79eb5` — **Count outline levels the way the menu does.** "Expand through level…" passed its
  1-based Level straight to `expandThroughDepth`, which takes the tree's 0-based `depth`,
  so every level showed one more than it said — Level 1 (Achieve's top row of result areas)
  expanded the roots and showed their children too. The mutation's own comment invited it,
  claiming to match Achieve's numbering while taking a depth; it now says which it takes.
  Checked against `docs/achieve-planner/online-help.md:3082` rather than guessing: "expand
  all rows until level N in parent/child hierarchy is reached and then collapse all
  remaining children". Conversion is a named, tested `depthForOutlineLevel`.

- `ef5c380` — **Keep one list of priority letters, and look the selected row up once.**
  `maintenance.ts` carried its own `["A","B","C","D"]` behind an `as PriorityLetter[]` cast
  while `letterRank.ts:26` already exports `PRIORITY_LETTERS`. Same values today, so nothing
  was broken — but the cast is exactly what would stop the compiler noticing if the enum
  widened. Also: the Chooser's `rowActions` found the selected node three times to fill two
  fields, the third behind a `!` that only held because the second `find` had just proved it.

- `9758165` — **Put a tripwire under the shared wall-clock date math.** `src/lib/dateMath.ts`
  is the single copy of the calendar arithmetic that appointment recurrence and task
  recurrence both sit on, and it had **no test of its own** — only whatever its callers
  happened to exercise. No bug found; 17 cases added for the rules that look right until a
  specific date: the month-end clamp (Jan 31 + 1 month is Feb 28, not Mar 3), leap and
  century rules, and going through local getters so 09:00 the day after a spring forward is
  still 09:00. Confirmed they earn their place by breaking the source two plausible ways —
  dropping the `addMonths` clamp and rounding `daysBetween` down instead of to nearest —
  which fails five of them including the DST span, then restored and re-ran green.

- **Say when the zoom picker is showing only the first 200 matches.** It capped its list and
  said nothing, so on an outline big enough to hit the cap a search would look like it had
  found everything there was. Named `PICKER_LIMIT`, and a line appears saying how many
  matched and that typing narrows it. The cap is applied before the selection resolves, so
  confirm still cannot land on a row that is not rendered.

## Needs a decision

- **Metrics is the only grid with no command deck** — it does not use `GridToolbar`, so it
  has neither the deck nor the `⋯` overflow the other twelve views share. Options: (a) move
  `MetricsView` onto `GridToolbar` like the others, which is the consistent answer but is a
  real refactor of a view with its own toolbar, or (b) leave it, on the grounds that a
  metrics catalog is not a record grid. **Recommendation:** (a), as its own small slice —
  it is the last holdout and the standard in `components/data-grid.md` reads as though every
  grid shares the control surface. Too big to start unattended.
  — blocking: nothing today; it is a consistency debt, not a defect.

- **The Task Chooser gets only Open/Rename**, synthesised from `rowActions`. That may be
  exactly right — it ranks tasks rather than holding records — or it may want the same
  conversion/priority commands the other node projections got through
  `useNodeCommandDeck`. **Recommendation:** leave it until you have used the deck for a few
  days; the Chooser is a read-mostly view and extra commands there could be noise.
  — blocking: nothing.

- **Tap targets in the outline's compact rows are 18–19px** (the ▶/▼ twisties), against the
  **44px minimum** `components/responsive.md` sets below `md`. Pre-existing — it came in with
  `6f25fa6 Render grids as card rows below md`, not tonight. The standard's own guidance is
  "where a compact layout needs the same action, it gets a new control at tap size — it does
  not shrink the desktop one", but honouring that changes mobile row density, which is a look
  decision. **Recommendation:** grow the hit area with padding rather than the glyph, and
  check it does not collide with the adjacent row's tap area at `390×844`.
  — blocking: nothing; noticed while verifying the deck on a phone viewport.

- **Converting a task to a project leaves its day line behind.** `convertNode` ends with
  `syncDayLinesInSubtree`, but `syncDayLineToTargetStart` (`src/lib/day/sync.ts:118`) selects
  `and(… eq(nodes.type, "task"))` and returns early for anything else — "not a task, so it
  has no target start date to follow". So an open `daily_items` row pointing at a node that
  has just stopped being a task is neither updated nor cleared, and `src/lib/day/queries.ts`
  has no type filter, so the Day page would list a Project among the day's tasks. Options:
  (a) clear open day lines for a node that leaves `task`, inside the same transaction;
  (b) filter the Day query to tasks; (c) do nothing, because Day may not survive.
  **Recommendation:** (a) — it is three lines in a transaction that already owns the
  cleanup of `taskCompletions` and `nodeItems`, and it fixes the data rather than hiding it.
  I did not do it unattended because your standing note is that **Day may be removed and new
  work should not be built on `daily_items`**, which makes this your call rather than mine.
  — blocking: nothing today; the row is stale, not corrupt.
