## Needs a decision

- **Settings ▸ Preferences tells you that 12 of your current preferences were "stored by an
  older or unrecognized Planner version".** Not a label nobody sees:
  `SettingsPage.tsx:418` prints that sentence under every row in the **Other** group, and
  `buildPreferenceGroups` run against your real `user_settings` puts **14 of your 36 rows**
  there — of which only two are actually legacy.

  ```
  ## Other (other) — 14
     budget                          | Budget setup       ← live (Budget start month / opening)
     find                            | Advanced Find      ← live
     grid:budget                     | Grid — Budget      ← live
     grid:budget-bills               | ...                ← live
     grid:budget-envelopes           | ...                ← live
     grid:budget-savings             | ...                ← live
     grid:finance-accounts           | ...                ← live
     grid:finance-bills              | ...                ← live
     grid:finance-payees             | ...                ← live
     grid:metrics-layout             | ...                ← live
     grid:supplies                   | ...                ← live
     timeline                        | Timeline           ← live
     grid:finance-commitments-bills  | ...                ← genuinely legacy
     grid:finance-commitments-spend  | ...                ← genuinely legacy
  ```

  Confirmed in the running app, not only in the function: **Settings ▸ Views & layout**
  renders fourteen rows carrying that sentence, under a heading reading **Other** with its own
  **Reset module** link. Screenshot: `.artifacts/planner-shots/settings-other.png`.

  The cause is one line. `moduleEntry` (`src/lib/settings/management.ts:87`) takes a grid
  scope's key, cuts it at the first `.`, and requires the remainder to be a key of
  `MODULE_LABELS` — a fifteen-entry list from before the module/page split. Every grid tab id
  added since (`budget-bills`, `finance-accounts`, `supplies`, `metrics-layout`, …) and every
  scope kind with no arm in that function (`budget`, `find`, `timeline`) falls through to the
  `other` bucket, whose `detail` is hard-coded to that sentence.

  Two consequences beyond the wrong words: resetting **Finances** does not reset any finance
  grid (its `resetScopes` is built from the entries it grouped), and every future grid lands in
  Other silently. The unit test does not catch it because its fixture's only Other case is a
  made-up `retired:layout` — no live-but-unlisted grid id
  (`management.test.ts:40`).

  There are three namespaces here and none of them agree: **module** ids
  (`plan`, `finances`, `library`, … — `components/shell/modules.ts`), **page** ids
  (`budget`, `accounts`, `payees`, … — `lib/navigation/pages.ts`), and **grid tab ids**
  (`finance-accounts`, `budget-bills`, `supplies`), which are their own namespace with a
  `finance-` prefix applied inconsistently. `management.ts` assumes the third equals the first.

  Options: **(a)** one registry in `src/lib` mapping every grid tab id to the page it belongs
  to, with a unit test asserting every id passed to `useGridState` / `useModuleViews` appears
  in it, and headings taken from `pages.ts`'s own labels; **(b)** rename the grid tab ids to
  match page ids — `modules.ts` already rejects this in writing ("renaming a persisted scope
  key would be a migration bought for nothing"), and it would orphan every stored row;
  **(c)** leave the grouping and only fix the sentence, so a row with a known scope kind stays
  in Other with an honest detail line.

  **Recommendation: (a), with (c) shippable tonight-cheap if you want the lie gone first.**
  (a) is the only one that makes the _next_ grid a test failure instead of another silent
  Other row, and it needs no migration. Not taken tonight because it decides which heading
  each grid sits under — "Budget bills" under **Budget** or under **Finances** is your call,
  and it changes the shape of a settings page you look at.
  — blocking: nothing. The two genuinely legacy `finance-commitments-*` rows are already
  resettable from that page; I did not touch your data.
