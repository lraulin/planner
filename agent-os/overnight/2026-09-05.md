- `7e16b7e` — **A bill charge landing exactly between two occurrences was credited to the
  later one.** `nearestOccurrence` (`src/lib/finances/billSchedule.ts:170`) documents "ties go
  to the earlier occurrence, which is the one already owed" but compared both directions with
  a strict `<`, so an exact tie stayed wherever `Math.round(monthsOut / cadenceMonths)` landed
  — forward. A monthly bill due the 15th charged on 2026-03-01 is 14 days from February's
  occurrence and 14 from March's (February being 28 days), and was credited to March;

  charge, so a whole cycle was skipped and February read as never paid. Backward now wins an
  equal gap. — verified by `billSchedule.test.ts` "breaks an exact tie toward the occurrence
  already owed" and "…when a lead shifts the postings" (both fail before the fix), with the
  24-posting real-rent-history regression still green.

  Worth knowing: the pre-existing test named "breaks a tie toward the occurrence already owed"
  compared 15 days against 16, so nothing exercised a tie at all.

- `8019ce2` — **A parent cycle crashed every grid with a Status column.**
  `scheduleStatusById` (`src/lib/tree/status.ts:263`) is the one downward walk in the tree
  code with no cycle insurance: `walkUp` covers every upward walk and `derive`'s rollup is an
  iterative reverse pass that skips a child it has not reached, both written for a cycle a
  corrupt import can create and `moveNode` refuses to. So `derive` hands the nodes over
  happily and `visit` recursed — it memoizes into `result` only _after_ the child loop, so
  re-entering an open node found nothing cached and A→B→A ran until the stack gave out. A
  `RangeError` out of a server component takes down Outline, Projects, Tasks, Goals and the
  Chooser. Open nodes are now tracked during the walk. — verified by `status.test.ts`
  "survives a parent cycle rather than exhausting the stack" and "still rolls a cycle's urgent
  child up to the node that reached it"; both raise `Maximum call stack size exceeded` with
  the guard removed.

- `e454bf0` — **The Projects grid's Tasks column hung on a project cycle.** Found by
  checking whether the pattern above repeated — it did, twice. `taskRatio`
  (`src/lib/tree/taskRatio.ts:30`) walks a subtree with an iterative stack and no `seen` set.
  Reachable because the walk is entered at the project's _own_ id, so it starts inside the
  cycle; a downward walk cannot otherwise enter one, since every member of a cycle has its
  parent within it. Worse than the stack overflow: the loop is synchronous and unbounded, so
  there is no error to surface — the request just never returns. — verified by a test that
  never returned before the fix, and `taskRatio.test.ts` "terminates on a parent cycle" plus
  "counts a task reached twice only once" (the fast signal for the same guard) after.
